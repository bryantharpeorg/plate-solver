# Imaging cameras come through INDI, the scope node relays their frames, and the console solves and stacks

The imaging camera at the main telescope's focuser is run by the scope node through an INDI server on the same machine, behind the camera port. The scope node takes each exposure and forwards the imaging frame untouched over the scope link, on its own connection; it does no pixel work. The console saves every frame, solves it with ASTAP behind a solver port, calibrates it and stacks it. We chose this so that any camera INDI drives works with no code of ours per model, the hardware-specific failure handling is INDI's and not something we can only test at the telescope, the scope node stays a small relay that today's board can carry, and the pixel maths stays on the faster machine as ADR-0001 already has it. The mount is not on INDI: ADR-0001 stands for the 16-inch Dob, because INDI's telescope interface works at the sky level and keeps its own alignment. A later telescope on an equatorial mount may come through INDI as its own design, and the imaging path is kept mount-neutral for it: imaging code reaches the mount only through GoTo, Track, Stop and a tracking error stated on the sky, takes each sub's rotation from its own solve, and is sized to no one focal length.

## Considered Options

- **Our own adapter over the camera maker's library.** Rejected for now: one maker only; the library is a closed binary that cannot be linked into the scope node's static build, so it needs a helper program anyway; none of that code can be tested without a camera. It stays possible later as another adapter behind the same port.
- **Stacking on the scope node.** Rejected for now: today's node lacks the memory, and the mount already stops when the console or the link drops, so stacking on the console adds no new dependency. A stronger node could host the console itself later without changing this split.
- **Our own hinted solver for imaging frames**, reusing the solver's verify and refine steps against a deep star catalogue. Rejected by the owner in favour of ASTAP: a proven program that several imaging tools call the same way, and one that needs no starting angle, which the first solve after the camera is seated cannot supply. The solver port keeps the other path open.
- **An existing live stacker called as a program.** Rejected: the only one that can be called has no outlier rejection, round-trips every frame through files and is labelled experimental by its own manual. Two permissively licensed Rust stackers exist and may be tried before the stacking spec is built.
- **A second aim point for the eyepiece.** Rejected: the eyepiece and the sensor share the focuser's axis to within a few arcminutes, and a measured value is better than a tapped one.
