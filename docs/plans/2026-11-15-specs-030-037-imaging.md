# Plan: specs for "ask for the Orion Nebula and get a picture" (030 → 037)

## Context

The finder console finds, reaches and follows a target with the finder camera's solves. The owner wants the next
part: an imaging camera at the main telescope's focuser, and one ask, from the page or an MCP client, that ends
in a stacked colour picture, in the manner of a smart telescope:

- the console relates what the finder camera and the imaging camera each see, with nothing to tap;
- it says whether focus is good (the focuser is manual);
- it drives the mount until the target is centred on the imaging camera's sensor;
- it takes short exposures, rotates and shifts each into place, and stacks them while the observer watches.

A `/grill-with-docs` session on 2026-11-15 settled every decision below. It wrote this plan,
`docs/adr/0002-imaging-cameras-through-indi-frames-relayed-console-stacks.md`, the `GLOSSARY.md` terms, the
research note `docs/research/2026-11-15-imaging-camera.md`, and eight draft spec trios, `specs/030-…` to
`specs/037-…`: seven at first, then eight when the owner asked for 030 to be split so that a builder reads a
shorter spec (030 kept the scope node's side and the link; 031 is the console's side).

**Carrying out this plan writes specs and docs only, no product code.** Each spec is built after the owner
flips it to `ready`.

**Read first:** `GLOSSARY.md`, both ADRs, `.specify/memory/constitution.md`, and the research note. The note
holds the facts, numbers and source links the specs cite; a behaviour not grounded there, in a cited source or
in the simulator's truth is invented (constitution I).

## Settled decisions

| Area | Decision |
|---|---|
| Who runs it | The console owns one procedure, the *imaging run*. The page's button and one MCP tool start the same run. An MCP client chooses, steers and stops; it does not sequence. Each step also has its own route and MCP tool. |
| Mount | Only the console's own GoTo and Track. No hand-controller mode. Imaging reaches the mount only through the console's GoTo and Track, never a mount protocol, so a later mount adapter touches no imaging code. |
| Where work runs | Relay-first. The scope node takes exposures and forwards each *imaging frame* untouched; the console saves, solves, calibrates and stacks. Forwarding at the camera's full resolution or binned 2 × 2 is a setting, and so is also saving each frame on a disk at the scope node. All MCP stays on the console (016's rule holds). |
| Camera access | Through INDI: the scope node is a client of an INDI server on the same machine, behind the camera port. Nothing is keyed to one camera model; capabilities are read from the camera. A simulator adapter stands in for tests. Another access path later is another adapter. |
| What is kept | Every sub, untouched, as a 16-bit FITS file, and the stack. Keeping subs is a per-run switch, on by default. |
| Imaging solver | ASTAP's command-line program and one of its star databases, on the console machine, behind a *solver port*. It solves every sub. A simulated solver adapter answers from the simulator's truth in tests and under `finder --simulate`. |
| Two cameras | One *aim point*: where the main telescope looks in the finder camera's frame, now the centre of the imaging camera's sensor. The console measures it, with the *imaging angle*, whenever an imaging solve and a live pointing share a moment. Tapping a star stays for nights without the imaging camera. |
| Focus | The *focus reading* is the median star size in the focus region, in arcseconds. Verdict against the *focus record*: good (within 10%), slightly soft (10–30% worse: warn, carry on), clearly out or unmeasurable (pause, open the *focus aid*). The observer can always say go anyway. No absolute "focus is good" is claimed. |
| Calibration | Dark and flat frames are in this pass: taking them, a *calibration library*, applying them, the bad-pixel map. Without a matching master a run still works and says what is missing. |
| Stacker | Built into the console. Registration comes from each sub's imaging solve. Outliers are rejected (satellite trails cross the showcase target's field routinely). |
| Tracking in a run | The finder gets the target there; during exposures the subs' imaging solves steer the tracker, and rate corrections change only between exposures. |
| Night | The stacked picture and every imaging preview are red-only in the night edition, with a hold-to-see-colour control: the one written exception to the Red Torch Rule. MCP clients get colour. |
| Another telescope later | The imaging path must carry over, unchanged, to a different telescope on a different kind of mount: the owner plans a refractor on an equatorial mount. Imaging code holds no alt-az arithmetic, no axis counts and nothing sized to one focal length. No equatorial code is written now. "Mount-neutral by design" below is binding on 032–037 and governs where a spec's own brief says otherwise. |
| Colour | Whether a UV/IR-cut filter sits in front of the camera is not known, and the camera's window passes infrared. Colour balance is therefore a measured, adjustable step (the background made neutral per channel, and per-channel gains the observer can set), never a fixed matrix for one sensor. |
| Order | 030 camera link (the scope node's side) → 031 imaging frames on the console → 032 imaging solve and aim point → 033 focus → 034 darks and flats → 035 live stack → 036 tracking from subs → 037 the imaging run. |

## Conventions for every spec

- **Format:** the trio of `specs/025-frame-capture/` is the model: frontmatter `state: draft` and
  `depends_on_landed`, Clarifications, Owner decisions, Owner approvals, stories with Given/When/Then scenarios
  whose Then names a committed test, FRs, success criteria, Assumptions, Work Graph; `plan.md` with Interfaces,
  Shapes that existing tests pin, Decisions and the alternatives rejected, Prerequisites, Plan traps, Risks and
  a Refinement Record; `tasks.md`.
- **Later specs cite code that does not exist yet.** 031–037 name interfaces from the plans of the specs they
  depend on. Each is re-anchored against `main` after its predecessors land and before it is flipped; its
  Prerequisites say so.
- **Tests:** every scenario states its oracle and tolerance (constitution III). Oracles here are the
  simulator's truth, worked examples, and saved captures (a recorded INDI conversation, ASTAP's real output
  files). New finder tests are modules of the existing test binaries. No story edits an existing test unless
  an owner approval names the edit.
- **Stories** are vertical slices whose diff stays under 64 KiB. A story that adds a dependency, a route, a
  proto message, a glossary term, a config key or a DESIGN.md rule names it for owner approval.
- **No `unsafe`.** Reaching the camera through INDI needs none.
- **Vocabulary:** the terms below, exactly.
- **Docs carry no machine names, processor counts, timings measured on the owner's machines, or network
  names.** Budgets are stated as things the tests or the bring-up probes measure.
- **Simulated sizes:** the simulated imaging camera is small by default (1236 × 822 pixels over the same
  0.75° × 0.50° field) so the test gate does not pay for 16-megapixel renders. One test per spec at most uses
  the real camera's size.

## Mount-neutral by design

The 16-inch Dob is alt-az. A later telescope will sit on an equatorial mount, where the sky does not rotate in
the frame, subs run to minutes, the mount tracks by itself and is corrected in small steps, and a German mount
flips at the meridian. None of that is built now. These rules keep it from needing a rebuild.

1. **Four actions and two answers, all in sky terms.** Imaging reaches the mount only through the console's
   GoTo to a target, Track on and off, Stop, and a *tracking error* handed to whatever tracker is running:
   east and north arcseconds on the sky at a stated time. The tracker gives two answers back: the longest
   exposure it allows (none where there is no field rotation), and whether it is steady enough to expose
   (today false during a backlash take-up and the keyhole pass; later during a meridian flip). 036 defines
   this as the one interface between the stack and the tracker. The alt-az arithmetic (parallactic angle, axis
   rates, field rotation) stays inside 015's tracker and `ephemeris`; no file under
   `crates/finder/src/imaging/` computes it or reads axis counts.
2. **Rotation between subs is whatever the imaging solves say:** none on an equatorial mount, steady on
   alt-az, half a turn after a meridian flip. The stack places each sub by the full transform between two
   imaging solves and never computes field rotation from time, site or pointing. 035's scenarios cover no
   rotation, a small rotation and a half turn.
3. **Nothing is sized to this telescope.** No 1800 mm, 0.55″ per pixel or 0.75° field in code. Scale comes
   from the first imaging solve; before that, from the camera's pixel size and a focal length setting.
   Thresholds are in arcseconds or relative to a measured value, tile and region sizes are fractions of the
   frame, and the star database's name is a setting.
4. **The hint for an imaging solve comes from a list of sources tried in order:** the live pointing carried
   through the aim point; the last imaging solve; the session's target; none, which means a wide search. A
   telescope with no finder camera still solves, and the aim point stays optional.
5. **The run speaks in mount-neutral words.** Its states are slewing, tracking, paused by the tracker, and so
   on, and its centring step asks GoTo to bring the target to the sensor's centre. It never nudges an axis.
6. **Nothing assumes subs of a few seconds.** The exposure is a setting bounded by the tracker's limit.
   Timeouts, queue lengths and the rejection's learning set are counted in subs or scaled by the exposure,
   never fixed in seconds.
7. **The tracking error's set point can move.** The run says where on the sensor it wants the target; today
   that is the centre. A later tracker can shift it between subs (dithering) with no change to the stack.

## Interfaces shared across the specs

Each spec's `plan.md` owns the detail of what it creates. These names are fixed here so the eight agree.

### Scope node (030)

- Module `crates/scope-node/src/imaging/`. The imaging side of the camera port is the trait `ImagingCamera`:
  `describe`, `status`, `apply` (a partial edit of the settings, answering all the settings in force),
  `expose` (one exposure on request, asked for with its exposure and a purpose label) and `abort`. Each
  answers a future and takes `&self`, so `status` and `abort` work while `expose` waits.
- `ImagingInfo`: model, serial when the camera gives one, sensor width and height in pixels, pixel size in µm,
  bits per sample, colour or mono and the Bayer pattern, exposure range, gain range and offset range where the
  camera has the control, supported binnings, whether it has a cooler.
- `ImagingSettings`: gain, offset, binning, region of interest, cooler on and set temperature.
- `ImagingFrame`: the samples exactly as delivered (little-endian, 8 or 16 bits), width, height, bits, Bayer
  pattern, exposure start and end on the node's clock, exposure, gain, offset, binning, sensor temperature,
  and the region of the sensor it covers (amendment 6).
- Adapters: `indi` (a client of an INDI server at a configured address, device named or the first camera
  found) and `simulated` (the scope node's own 64 × 48 stand-in with no sky). `SimImagingCamera` in
  `crates/simulator` is the camera `SimNode` attaches, and so the one `finder --simulate` sees (amendment 4).
- Config: an optional `[imaging]` table (`adapter`, `address`, `device`, `save_dir`, `neutral`). `neutral`
  names the controls the INDI adapter sets to their neutral values each time it connects (amendment 2).
  Without the table the node has no imaging camera.
- `scope-node --probe-camera` describes the camera, takes three exposures and prints each one's size and the
  time from end of exposure to frame in hand; `--probe-exposure-ms` sets the exposure.

### Scope link (030)

A new service, `ScopeNodeImaging`, in `scope_node.v1` (a new service, as 025 added `ScopeNodeRaw`, so
hand-written implementations of the older services keep compiling):

| RPC | Request → reply |
|---|---|
| `DescribeImaging` | → `ImagingInfo` |
| `ImagingStatus` | → `ImagingStatusReply`: temperature, cooler power, set temperature, whether an exposure is in progress |
| `ConfigureImaging` | `ImagingSettings` → the settings in force |
| `Expose` | exposure in ms, a purpose label, the most bytes of samples to forward a second (0 for no limit) and whether the node also keeps the frame → a stream: one header (frame id, size, bits, pattern, region, times, settings, temperature, byte count, purpose, and the name of the node's own copy or why there is none), then data chunks of at most 256 KiB |
| `AbortExposure` | → empty |

The console opens a second connection to the node for this service, so frame bytes never share the heartbeat's
connection. A node without an imaging camera answers `FAILED_PRECONDITION`, for `Expose` as the stream's first
and only item; an older node answers `UNIMPLEMENTED`.

### Solver port (032)

- `trait ImagingSolver`: `name()`, `solve(frame, hint) -> ImagingSolve` and `measure(frame, region) ->
  StarMeasure` (median half-flux diameter in the frame's pixels and star count).
- `SolveHint`: where it came from (`pointing`, `last_solve`, `target` or `none`), RA and Dec, search radius,
  field height when known. The place is the finder camera's live solve nearest the exposure, carried through
  the aim point; else the last imaging solve; else the session's target; else none. The radius is 3°, or the
  sensor's diagonal on the sky for a hint from a live solve once the aim point is measured; with no place the
  whole sky is searched. The field height comes from the kept scale, before one from the camera's pixel size
  and `--focal-length-mm`, and with neither is left to the solver.
- `ImagingSolve`: J2000 RA and Dec of the frame centre, the angle of frame-up east of north, arcseconds per
  pixel, whether the frame is mirrored, its linear part in degrees a pixel, the frame's size, the matched star
  count when the solver gives one, time taken.
- Adapters: `astap` (runs the program on a prepared copy of the saved FITS file in a work folder, reads its
  `.ini`, maps its exit codes) and `simulated` (in `crates/finder`, answering from the simulator's imaging
  truth).
- Console flags `--astap`, `--astap-db`, `--astap-db-name` and `--focal-length-mm`. Without `--astap` (which
  needs `--astap-db-name`; `--astap-db` is optional), and outside `finder --simulate`, an imaging solve answers
  `this console has no imaging solver`.

### Simulator (030, extended by each spec that needs more)

`SimImagingCamera` renders 16-bit Bayer frames along the main telescope's axis: stars drawn from a seeded deep
field around the pointing, a point-spread function widened by a focus error, smear from the mount's motion
within the exposure, field rotation, sky background, read and shot noise. It gives the imaging truth (the
frame's true centre, angle and scale at a time) and carries the focus error in its optics. Later specs add: a
control that turns the simulated focuser, and seeded measure noise and a sharpest point on the simulated
solver (033); hot pixels, a column pattern, vignetting, dust shadows, a cover and a flat panel (034); a
satellite streak and a faint extended source (035); a memory of where the telescope pointed, so that the truth
of a past instant is right on a moving mount, and count steps on the simulated mount (036). 032 adds nothing
here: its simulated solver reads 030's truth. `finder --simulate` gets the simulated imaging camera and
solver.

## 033-focus-reading-and-aid

The focus reading through the solver port's `measure`, the focus region chosen as the tile of a full frame

Field checks: the reading falls and rises through focus as the knob turns; the in-focus value for this
telescope and camera is written down.

## 034-dark-and-flat-frames

Taking darks (refused when the frames are not dark, unless the observer says to take them anyway) and flats
(exposure set from the frame's level), master frames, the calibration library, a master dark keyed by camera,
gain, offset, binning, set temperature and exposure, and a master flat by camera, frame size and origin, bits,
Bayer pattern and binning only (the owner's departure of 2026-11-17: a master flat has its own dark taken off,
so gain, offset and set temperature do not change it); the bad-pixel map; `calibrate(sub)` with its fallback of repairing hot pixels from the sub itself;
the page block and three MCP tools.

Field checks: a dark set and a flat set taken on the real camera; a calibrated sub compared with the raw one.

## 035-live-stack

Each sub calibrated, turned into colour, placed by its imaging solve onto the first sub's grid, and
accumulated with a coverage weight and outlier rejection; a background model, colour balance and stretch for
display; the stack saved as 32-bit FITS and PNG with `stack.json`, which lists every sub and what became of
it; subs that fail to solve or measure poorly dropped and counted
with the reason; the picture on the Imaging page. It runs on whatever the camera is pointed at while the
console tracks, so it is usable before 037.

Field checks: a stack of a bright cluster and of the Orion Nebula; a satellite trail rejected; corners after
half an hour of field rotation.

## 036-tracking-from-subs

While a stack is running, each accepted sub's imaging solve gives the target's offset on the sensor; that
replaces the finder's live pointing as the tracker's error signal. Rate corrections are issued between
exposures. The tracker's two answers reach the stack through one interface: the longest exposure it allows
(on this mount, 015's figure for a chosen smear) caps the exposure setting, and while it reports that it is
not steady (on this mount, take-up at a reversal and the keyhole pass) the stack pauses exposures.
`PUT /api/imaging/steering` sets the corner smear and whether the subs steer. A sub taken while the tracker
was not steady is dropped.

Field checks: drift across the sensor per sub with and without the feedback; a run through the meridian.

## 037-imaging-run

One ask: GoTo on the finder, Track on, a first imaging frame, the focus check (before the first imaging solve,
because an unfocused frame does not solve), the imaging solve and the measured aim point, centring on the
sensor to tolerance, by Track off, which puts the newly measured aim point in force, and Track on again, so
that GoTo brings the target to it,
stacking with tracking from the subs, and safe endings (stopped, a limit reached, too low, Sun up, link lost,
a mount, camera, solver or stack failure, a failed save, a focus pause left too long, a target changed or not
centred, subs that keep being dropped, the telescope pushed away by hand). The page's Start and Stop, the run's state line and
counts, and four MCP tools.

Field checks: the whole run on a bright target, started once from the page and once by an MCP client.

## Amendments after 030, 031, 032 and 034 were drafted and reviewed

The three trios (030 and 031 were one trio then) were drafted, reviewed by a second agent and fixed. Where a
trio's reviewed text is more exact than this plan, the trio's `plan.md` is the interface; the points below are the ones that reach across
specs.

1. **One holder of the camera at a time.** A single frame, the focus aid, a calibration set, a stack and an
   imaging run all take exposures. The console's imaging state (031) holds one lease naming the holder; a
   second taker is refused with the holder's name. Each later spec takes and releases that lease and adds no
   lock of its own.
2. **White balance.** Where a camera offers white-balance controls they scale the raw samples. The INDI
   adapter (030) sets each to its neutral value once, when it connects, so every frame of every night is on
   the same footing for calibration. No spec records them per frame.
3. **Storage root.** Everything the console keeps for imaging lives under one folder, `imaging/` in the
   state folder or the folder `--imaging-dir` names: `frames/`, `calibration/`, `runs/` inside it. Files are
   named by the console's own frame id.
4. **Two stand-in cameras.** The scope node carries a tiny built-in one for `adapter = "simulated"`; the
   simulator crate carries `SimImagingCamera` with a sky. Tests of the node alone use the first, everything
   that needs stars the second.
5. **The forwarding rate limit** is a console setting sent with each exposure, not a node config key.
6. **A region of interest is recorded with the frame** (its origin and size on the sensor, in the header and
   the FITS file), since later specs solve and measure regions.
7. **Dependencies between the specs** are what each trio's `depends_on_landed` says after review, not only
   the order in "Settled decisions".
8. **A push by hand is followed, not undone (2026-11-16).** The owner asked that a push away from the target
   while Track is on should not be pulled back. Spec `038-track-follows-a-push` changes 015's Track so a push
   of more than 5′ that is then left still is followed and shown, and turning Track on again goes back. It needs nothing of 030–037
   and can land first. 037 ends its run `pushed_away` when Track shows a push. 036, re-anchored after 038
   lands, must end the subs' claim on the tracker when Track follows a push.
